# אבטחה, זהות משתמש ובידוד בין חשבונות – FocusMind AI

המסמך מסכם את סקירת האבטחה שבוצעה לפני ההגשה, את מה שתוקן ואת הבדיקות האוטומטיות שמוכיחות את ההתנהגות.

## איך מזוהה המשתמש המחובר
1. בהתחברות השרת בודק את הסיסמה (bcrypt) ומחזיר עוגייה בשם `focusmind_access_token`. העוגייה:
   - **HttpOnly**: JavaScript לא יכול לקרוא אותה;
   - **SameSite=Lax**;
   - **Secure** בייצור;
   - מוגבלת לנתיב `/api`.
2. העוגייה מכילה JWT חתום (HS256) עם השדות `sub` (מזהה המשתמש), `iat`, `exp` ו-`jti` (מזהה ייחודי של ההתחברות).
3. בכל בקשה ל-API השרת:
   - מאמת את החתימה, את האלגוריתם ואת התפוגה;
   - בודק שה-`jti` לא בוטל בהתנתקות;
   - טוען את המשתמש מהמסד.
4. **השרת לעולם לא מקבל מזהה משתמש מהדפדפן.** אין `userId` ב-URL, ב-query או בגוף הבקשה. שדות לא מוכרים (כמו `ownerId` או `role`) נדחים (422) או מתעלמים מהם.
5. הדפדפן לא שומר את הטוקן ב-localStorage. הממשק מקבל את פרטי המשתמש רק מ-`GET /api/auth/me`.

## האם מזהה המשתמש צריך להופיע ב-URL?
לא, וגם אין צורך.
- **"שלי"** (הלוח, הקורסים שלי, התובנות, החזרה החכמה) נקבע לפי העוגייה בשרת, ולכן הכתובות זהות לכל המשתמשים: `/dashboard`, `/courses`, `/insights`.
- **מזהי אובייקטים** (קורס, שיעור, קטע ReplayAI) כן מופיעים בכתובת, כי אלה כתובות של משאב. כל פעולת API עליהם בודקת בעלות או הרשאה בשרת. שינוי המזהה בכתובת לא נותן גישה.

### תבניות הכתובות בפועל
| כתובת | גישה |
|---|---|
| `/`, `/register`, `/login` | ציבורי |
| `/dashboard`, `/courses`, `/courses/catalog`, `/courses/new` | מחובר |
| `/courses/:courseId` | הבעלים של קורס אישי. קורס קטלוג מפורסם: כל משתמש מחובר |
| `/courses/:courseId/edit` | הבעלים של קורס אישי, או מנהל תוכן בקורס קטלוג |
| `/learning/lessons/:lessonId` | הבעלים, או מי שרשום לקורס הקטלוג |
| `/learning/lessons/:lessonId/review/:itemId` | רק מי שהקטע שייך לו |
| `/learning`, `/review`, `/insights`, `/study`, `/privacy` | מחובר (הנתונים של המשתמש בלבד) |
| `/admin/catalog` | מנהלי תוכן. ההרשאה נבדקת בשרת |

## בידוד הנתונים בין חשבונות
- כל אוסף פרטי נשמר עם `user_id` או `owner_id`, וכל שאילתה מסננת לפי המשתמש מהעוגייה. זה נכון ל:
  - קורסים אישיים, שיעורים וסרטונים;
  - התקדמות;
  - מפגשי למידה ומקטעי קשב;
  - קטעי ReplayAI וסימניות;
  - שאלות ותשובות;
  - מטרות לימוד;
  - העדפות.
- אובייקט של משתמש אחר מחזיר **404** ("לא נמצא"), ולא 403. כך אי אפשר אפילו לדעת שהוא קיים, ותוכן השגיאה לא חושף פרטים.
- בקורס קטלוג משותף, ההתקדמות, הקשב, ReplayAI והשאלות נשמרים לכל לומד בנפרד.
- **סרטונים שהועלו:**
  - מוגשים רק דרך `/api/videos/{id}/stream`, אחרי בדיקת הרשאה;
  - אין כתובת ציבורית לקובץ;
  - שמות הקבצים בדיסק אקראיים, ושם הקובץ מהמשתמש לא משמש כנתיב.
- **הרשאות מנהל:**
  - ניתנות רק משורת הפקודה (`python -m app.admin grant`);
  - כל פעולת קטלוג נבדקת בשרת ומחזירה 403 ללומד, גם בבקשה ישירה.

## מה תוקן בסקירה הזו
| ממצא | חומרה | תיקון |
|---|---|---|
| התנתקות מחקה את העוגייה רק בדפדפן. טוקן שהועתק לפני ההתנתקות המשיך לעבוד עד שפג תוקפו | בינונית | `jti` בכל טוקן, ואוסף `revoked_tokens` עם TTL. בהתנתקות הטוקן מבוטל בשרת |
| תשובות API פרטיות בלי `Cache-Control: no-store`. דפדפן או proxy עלולים לשמור אותן, ואז Back אחרי התנתקות או משתמש אחר באותו דפדפן יכולים לראות אותן | בינונית | Middleware שמוסיף `no-store` ו-`Pragma: no-cache` לכל `/api` |
| אין בדיקת מקור (CSRF) מעבר ל-SameSite=Lax | נמוכה (הגנה נוספת) | בקשת כתיבה עם Origin של אתר אחר, או `null`, נחסמת ב-403 |
| חסרו כותרות אבטחה | נמוכה | `X-Content-Type-Options`, `X-Frame-Options: DENY`, `Referrer-Policy`, `Permissions-Policy`, ו-Content-Security-Policy לדפי האתר בייצור |
| בממשק: 401 באמצע שימוש (התנתקות בלשונית אחרת או טוקן שבוטל) לא הוציא את המשתמש. התנתקות שנכשלה ברשת השאירה את הנתונים על המסך | בינונית | 401 מכל בקשה מסיים את הסשן בממשק. ההתנתקות מנקה את המסך תמיד. BroadcastChannel מסנכרן התחברות והתנתקות בין לשוניות. בשחזור עמוד מה-bfcache (Back/Forward) יש בדיקה מחודשת מול השרת |
| החלפת חשבון בלי רענון יכלה להשאיר מצב רכיבים של המשתמש הקודם | נמוכה | העמודים המוגנים מקבלים `key` לפי מזהה המשתמש, ולכן נבנים מחדש |

## מה נבדק ונמצא תקין (בלי שינוי)
- **JWT:**
  - האלגוריתם קבוע (HS256 בלבד);
  - חתימה זרה, טוקן בלי `exp`, טוקן שפג תוקפו ומשתמש שנמחק נדחים;
  - `SECRET_KEY` חייב להיות באורך 32 בתים לפחות.
- **סיסמאות:** bcrypt עם SHA-256 מקדים, שעוקף את מגבלת 72 הבתים של bcrypt.
- **ניסיונות התחברות:** הזמן זהה לאימייל קיים ולאימייל שלא קיים. יש הגבלת קצב להתחברות ולהרשמה.
- **IDOR:** נבדקו כל נתיבי ה-API עם מזהים של משתמש אחר, בכל מתודה (GET, POST, PUT, PATCH, DELETE).
- **XSS:**
  - React מציג טקסט כטקסט;
  - אין `dangerouslySetInnerHTML`;
  - קישורים חיצוניים מוגבלים ל-`https`;
  - יש CSP.
- **SSRF:**
  - השרת לא מוריד כתובות שהמשתמש מזין. הוא רק שומר אותן, והדפדפן מנגן.
  - כתובות IP, `localhost` ורשתות פרטיות נדחות.
  - כלי בדיקת הסרטונים של הקטלוג רץ רק משורת הפקודה של המנהל.
- **העלאות:**
  - סוג הקובץ נבדק לפי התוכן (MP4 או WebM), לא לפי הסיומת;
  - יש מגבלת גודל ומכסה למשתמש;
  - הקבצים נכתבים לקובץ זמני ואחר כך עוברים rename;
  - מנגנון הגשת קובצי האתר חוסם path traversal.
- **CORS:** בייצור הרשימה ריקה (`[]`), כי הכול באותו מקור.

## סיכונים שנשארו בכוונה
- **בדיקה אם אימייל רשום:** ההרשמה מחזירה "האימייל כבר רשום" (409). זה מאפשר לבדוק אם אימייל קיים במערכת.
  - הסיבה: בלי אימות אימייל במייל, זו הדרך להסביר למשתמש מה קרה.
  - מה מצמצם את הסיכון: הגבלה של 20 הרשמות לשעה לכל כתובת IP.
- **הגבלת הקצב נשמרת בזיכרון של כל instance.** בכמה instances של Cloud Run כל אחד סופר בנפרד.
- **התנתקות ברשת שנפלה:** הממשק מתנקה, אבל הטוקן לא בוטל בשרת. הוא פג אחרי `ACCESS_TOKEN_TTL_MINUTES` (ברירת מחדל: 120 דקות).
